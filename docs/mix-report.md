# docs/mix-report.md — 阶段一混音（纯人声）实现说明 + 对齐误差实测报告

> 归属：`t8 [T2.2]`（audio-engineer）。用户 2026-09-23 裁决：**分两阶段** —— 本任务只做**阶段一：纯人声、无伴奏**。
> 阶段二（叠加伴奏 + 按固定时间轴对齐）等用户交付曲库后另派；本实现已把"拼接策略"做成**可替换函数**，阶段二只换实现。
> 产品规则以 `CONTEXT.md` 为准，架构决策以 `docs/architecture.md`（D-05 / ADR-015 §16.6）为准，音频链路总览见 `docs/audio.md`。

---

## 1. 成品是什么（阶段一）

**成品 = 按「歌里的固定段号 1..totalSegments」升序，把各段人声首尾相接，缺口处留等长静音，编码为 WAV。**

- **没有任何伴奏轨道**（阶段一硬约束）。曲库素材在 `apps/web/public/library/`，属阶段二（t13）。
- 导出格式 **WAV / PCM16**：纯 JS 可写、可逐字节回读校验（测试就是这么验的），且不需要实时录制。
  体积：单声道 48kHz ≈ 96KB/秒（90 秒 ≈ 8.6MB）。要压体积时在 `MixedPcm` 之上换编码器即可。
- 产出可**试听**（`<audio controls>` 指向 objectURL）与**下载**（`<a download>`，文件名带缺口标注）。

## 2. 语义决策（每条都有测试钉住）

| #   | 决策                                                                                                          | 理由 / 出处                                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 1   | **段号永不压缩、永不重编号**：缺第 2 段时第 3 段仍待在第 3 段的时间槽                                         | ADR-015 §16.1；否则阶段二接回伴奏时整条时间轴错位（§15.1 问题 2）                                    |
| 2   | **缺口 = 静音占位 + 显式标注**（`missingSegmentIndexes` + 「缺第 N 段」文案 + 文件名标注）                    | §16.6「严禁静默拼出看似完整但错位的成品」                                                            |
| 3   | 缺口占位时长优先级：**歌的分段元数据** → 已录段时长**中位数** → **22.5 秒**（15–30 秒区间中值）               | 静音长度尽量等于"那段本该多长"；来源写进 `durationSource` 便于追溯                                   |
| 4   | **时间轴唯一真相是帧**（整数 `startFrame`/`durationFrame`），毫秒由帧派生                                     | 相邻段 `startFrame[i+1] == startFrame[i]+durationFrame[i]`，不留缝、不重叠、不跨段累积漂移           |
| 5   | 脏数据**报出来**而不是静默处理：重复段号 / 段号越界 / 时长非法 / 一段都没有                                   | 界面能显示"为什么要这样拼"，而不是让用户面对一个可疑成品                                             |
| 6   | 混音用**复制**（不做叠加）                                                                                    | 计划保证段间首尾相接、互不重叠，因此不存在混叠；复制还能让"某段的值只出现在自己的区间"成为可断言性质 |
| 7   | 渲染双路径：`OfflineAudioContext`（D-05 产品路径）+ **纯 JS PCM 混音**（无 AudioContext 时自动降级 / 测试用） | 两者消费同一 `MixPlan`，输出格式一致；降级不改变成品语义                                             |

时间轴示例（4 段 × 22.5 秒，**缺第 2 段**）：

| 段号 | 类型    | 起点    | 时长  | 成品里的内容                                     |
| ---- | ------- | ------- | ----- | ------------------------------------------------ |
| 1    | voice   | 0.000s  | 22.5s | 发起者的人声                                     |
| 2    | **gap** | 22.500s | 22.5s | **静音**（位置保留，等补位者）                   |
| 3    | voice   | 45.000s | 22.5s | 第 3 段接唱者的人声（**没有**被前移成"第 2 段"） |
| 4    | voice   | 67.500s | 22.5s | 第 4 段接唱者的人声                              |

## 4. 对齐误差实测报告（D-05 客观验收：段落起拍误差 ≤ 120ms）

**测法**：合成 4 段 × 22.5 秒（48kHz 单声道，缺第 4 段），按计划混音（4 320 000 帧 = 90 秒），
再用 `measureClipOnsets` 逐样本找每段起拍位置，与计划起点比较，最后用 `summarizeAlignment` 按 120ms 判定。

```bash
pnpm --filter @music-drift/web test          # 用例名：对齐误差实测（合成信号，4 段 × 22.5s @48kHz）
```

原始输出（`console.warn`，逐字复制）：

```text
[mix-report] 无延迟: 总帧 4320000 / 90.0s · 段数 4（缺口 4） · 最大误差 0.000ms · 平均 0.000ms · 阈值 120ms · 达标 · 非静音缺口 [] · 纯 JS 混音耗时 3.4ms
[mix-report] 模拟 40ms 解码延迟: 总帧 4320000 / 90.0s · 段数 4（缺口 4） · 最大误差 40.000ms · 平均 40.000ms · 阈值 120ms · 达标 · 非静音缺口 [] · 纯 JS 混音耗时 3.7ms
[mix-report] 模拟 150ms 延迟: 总帧 4320000 / 90.0s · 段数 4（缺口 4） · 最大误差 150.000ms · 平均 150.000ms · 阈值 120ms · 未达标 · 非静音缺口 [] · 纯 JS 混音耗时 2.7ms
```

| 情形                                                     | 最大起拍误差  | 判定                          | 说明                                                               |
| -------------------------------------------------------- | ------------- | ----------------------------- | ------------------------------------------------------------------ |
| ① 段音频从第 0 帧起响                                    | **0.000ms**   | 达标                          | 本实现的**数学上限**：段落在整数帧上、首尾相接，因此不存在累积漂移 |
| ② 段音频自身前 40ms 是静音（模拟解码器 priming/padding） | **40.000ms**  | 达标                          | 距 120ms 阈值仍有 3× 余量                                          |
| ③ 段音频自身前 150ms 是静音                              | **150.000ms** | **未达标**（列出 3 个违规段） | 报告会明确列段，作为"是否提案 ffmpeg"的依据                        |

**结论**：规划 + 混音这一侧的对齐误差为 **0ms**（样本级精确），120ms 阈值由"音频源本身的前导静音"
（解码器延迟）决定余量。**未触发 ffmpeg 回退条件**（D-05：客观 >120ms 或主观盲听错位才允许提案回退）。

### 4.1 这份报告**没有**测什么（诚实边界）

1. **真机解码延迟未实测**：本会话没有浏览器，40ms/150ms 是**注入的前导静音**，不是从真实
   Chrome/Safari 录制的 webm/mp4 上测出来的。真实值取决于容器与解码器（AAC 的 priming 通常几毫秒到
   几十毫秒量级），**必须由 t14（qa-e2e）在真机上用真实录音复测**：把 `measureClipOnsets` 接到真实
   `decodeAudioData` 结果上即可（接口已就绪：`decode` 是注入端口）。
2. **主观盲听**（"有没有节拍错位"）需要人耳，属用户验收。
3. **`OfflineAudioContext` 路径的调度语义**只断言了"每段 `start(秒)` 与计划一致、缺口不调度、段只调度一次"
   （假上下文），未在真机上测 `startRendering()` 的实际样本落点 —— 这也是 t14 的复测项。
4. 阶段二所需的**伴奏时间轴对齐**未做（无曲库，用户未交付）。

### 4.2 防护验证（变异测试：证明测试真的会咬）

「测试全绿」不等于「规则被钉住」。下面是把**真实会犯的错**注入实现后跑测试的结果：

| 变异   | 注入的错误                                               | 结果                                                                           |
| ------ | -------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **M1** | 缺口不占位（只拼有效段 —— §15.1 的"压掉空洞"）           | **10 条失败** ✓ 被钉住                                                         |
| **M3** | M1 + 按列表位置重编号（= 完整的"压缩式"错误实现）        | **6+ 条失败**（含「缺第 2 段…段号不压缩」「多缺口」「段数来自数据」） ✓ 被钉住 |
| **M4** | 混音时忽略 `startFrame`、按顺序紧挨着摆                  | **9 条失败**（含成品 WAV 缺口静音断言） ✓ 被钉住                               |
| **M5** | 人声段按"过滤后的顺序"重新编号（阶段二最危险的那种改法） | **4 条失败**，含**不变式 A/B** ✓ 被钉住                                        |
| M2     | 仅把"缺口段号"写成 `clips.length + 1`                    | 25 条全过 —— **M2 改变的可观测面：无**（见下方差分证据）                       |

结论：**危险的错误（把缺口压掉 / 按拼接顺序重编号 / 不按段号时间槽摆放）全部能被测试抓到**；
M2 例外，且已用差分证明它不改变任何可观测输出。
**M2 的差分证据（可证伪的测量，不是论证）**：对 10 组输入（完整 4 段 / 缺 2 / 缺 2+3 / 5 段缺 2,3,4 / 只有第 2 段 / 乱序 / 空 / 重复段号 / 越界段号 / 非法时长），
把实现分别按"原版"与"M2 变异版"各跑一遍，dump 出 `clips[{index,kind,startFrame,durationFrame,startMs,durationMs,durationSource}] + totalFrames + missingSegmentIndexes + isComplete + hasAccompaniment + warnings`：

```bash
# 原版 → /tmp/m2-baseline.json（507 行）；施加 M2 → /tmp/m2-mutated.json；再对比
diff /tmp/m2-baseline.json /tmp/m2-mutated.json   # → 空（无差异）
cmp  /tmp/m2-baseline.json /tmp/m2-mutated.json   # → 字节级相同
```

**为什么必然相同**：规划层对 `1..totalSegments` 每个段号**恰好产出一个 clip**，因此在"推入缺口"那一刻恒有
`clips.length + 1 === index` —— 两个表达式在该位置的取值永远相等，M2 是**等价程序**
（变异测试只能发现行为变化，所以它活下来是正常的，不是覆盖漏洞）。

**为什么这条必须写进报告**：`clip.index` 在阶段一还是"信息性"的（成品按帧顺序首尾相接，index 变了成品也不变），
但**阶段二用它驱动伴奏的固定时间槽** —— 同一个改动到那时会让成品整条时间轴错位（§15.1 问题 2 的同一机制）。
因此本轮**新增两条不变式测试**（`mix.test.ts`「阶段二依赖的两个不变式」）把这条钉在阶段二之前：

- **不变式 A**：`clips[i].index === i + 1`（1..N 每个段号恰好产出一个 clip，缺口也占位）；
- **不变式 B**：人声 clip 的段号 = 该音频**源段**的段号（不是"第几个被拼进去的"）。

红证据：M1（压掉空洞）→ 6 条失败；**M5（过滤后顺序编号）→ 4 条失败，含 A/B 两条**。

## 5. 阶段二怎么接（只换策略，不改调用方）

```ts
// 阶段一（现在）
const plan = planMonoSequentialMix({ segments, totalSegments, sampleRate });

// 阶段二（拿到曲库后）：同一个签名，换一个 MixPlanner
const plan = planMix(planAccompanimentTimeline, {
  segments,
  totalSegments,
  sampleRate,
  nominalDurationByIndex, // 歌的固定段落时间轴（songSegments.durationMs）
});
```

`MixPlan` 已有 `hasAccompaniment` 与 `durationSource` 字段，阶段二只需在 clips 里叠加伴奏轨道信息；
`useMixExport` / `MixExportPanel` / WAV 导出 / 对齐测量**都不用改**。

## 6. 与其它任务的接口

- 消费 `GET /api/segments/:id/audio`（t7 的 Range 端点）取每段音频；段号与时长来自
  `BottleDetail.segments[].index` / `.durationMs`（服务端权威，前端不推算）。
- 上传协议（ADR-018：原始二进制）**已修好并通过端到端验收**（跨会话 Range 取回 + 字节级一致 + `octet_length` 对齐 + 负向对照）。
  当前真正的缺口不是协议，而是**库里还没有任何真实录音** —— 需要**真实浏览器**跑一次首录（会话内无浏览器）。
  在那之前，成品导出会走"缺音频"路径并**如实告警**（不会假装成功）。
- 页面组装（把 `MixExportPanel` 放进公海详情 / 漂流日志）归 t11。
